# 归属与转交（Ownership & Handoff）—— 让「有回复了」找到「该回的人」

> 配套阅读：**[跨会话 agent 通信](cross-session-inbox.md)**（那份讲"怎么给别的会话留话"）、
> **[在办台账](workboard-conventions.md)**（那份讲"怎么让所有人看见同一件事"）。
> 这一份讲**第三件事**：一件**对外的事**（issue / PR / discussion）**该由谁去回**。

---

## 一、问题：「有回复了」和「该谁回」是**两件事**

一条对外提交物收到回复时，会同时撞上两个**完全不同**的问题：

| 问题 | 由什么回答 | 防的是什么 |
|---|---|---|
| **我回过没有？** | 一条判据（"我最后一条发言之后，有没有别人发的新内容"） | 防**重复回复** |
| **该谁回？** ← 本文 | **归属表** | 防**没有上下文的人顶上去回** |

**两者互补、不重叠 —— 而且都得有。** 只有前者，会出现"谁都能回、于是回得零零碎碎"；
只有后者，会出现"该回的人不在，别人又不敢碰"。

**为什么"该谁回"是真问题**：**只有当初提交它的那只会话握着调查上下文。**
别人接手要重读一遍历史，而且**很容易读漏** —— 我们实测过：一只会话差点去回一条**自己已经回过**的话题。
⇒ 反过来，**归属表就是"上下文"的索引**：`context[]` 字段写明落点，
**原提交者不在时，任何会话照着它就能接手** ✓

## 二、数据文件：一张小表

**键** = `<owner/repo>#<number>` —— **issue / PR / discussion 用同一套键格式**（discussion 也有 number）。

**值**：

| 字段 | 说明 |
|---|---|
| `kind` | `issue` / `pr` / `discussion` ⚠️ **必填** —— 有的仓库 **issues 区是关着的**（只有 Discussions）。看到编号别想当然去 `/issues/<n>` 找 |
| `session` | 提交者会话标识（与你的信箱文件名对得上） |
| `sessionTitle` | 会话标题 —— **用于提示人类时的"多线索指认"**（见第八节） |
| `submittedAt` / `url` / `title` / `state` | 提交时间 / 链接 / 标题 / `open`·`closed`·`degraded` |
| `context[]` | **上下文落点清单**（记忆条目 / 工作区路径 / 台账行）—— 原提交者不可用时，任何会话照它就能接手 |
| `notes` | 备注（例如"同一仓库那两条线已闭环，别再叫醒它"） |

**完整示例**（可直接拿去做 `issue-owners.example.json`）：

```json
{
  "version": 1,
  "why": "对外提交物（issue / PR / discussion）的归属表：作者回复时，应转交给当初提交它的那只会话 —— 因为只有它握着调查上下文。",
  "howToRead": [
    "键 = <owner/repo>#<number>（discussion 也有 number，同一套键格式成立）",
    "值.kind = issue | pr | discussion —— ⚠️ 必填：有的仓库 issues 区是关着的，看到编号别去 /issues/<n> 找",
    "值.session = 提交者会话标识（与信箱文件名对得上）",
    "值.context = 上下文落点清单；原提交者不可用时，任何会话照它就能接手",
    "回复到达时：先查本表 → 转交 session；并提示用户（必须多线索：会话标题 + 时间 + 项目名，别只给 id）"
  ],
  "cleanup": [
    "① 已闭环（无人再回 / 原提交者已回复且对方未追问）⇒ 删掉该项",
    "② 原提交者会话已归档 ⇒ 保留但把 state 标为 degraded（对应降级分支：任何会话可接手）",
    "③ 硬上限 40 项；超出时先清 state=closed 且 degraded 的"
  ],
  "relationToOtherChecks": [
    "本表只回答『该谁回』。『我回过没有』在那条判据里。",
    "两者互补、不重叠；若将来要合，请一起合。"
  ],
  "owners": {
    "owner/repo#123": {
      "kind": "issue",
      "session": "<your-session-id>",
      "sessionTitle": "（会话标题）",
      "submittedAt": "2026-01-01T12:00:00+08:00",
      "url": "https://github.com/owner/repo/issues/123",
      "title": "（提交物标题）",
      "state": "open",
      "context": ["记忆条目：（主题）", "工作区：/path/to/audit/", "台账：workboard 里那一行"],
      "notes": "（可选）"
    }
  }
}
```

**三个顶层约定字段**（别省）：`howToRead[]`、`cleanup[]`、`relationToOtherChecks[]` ——
它们让**下一个读这张表的人**知道怎么读、什么时候删、以及它**不负责**什么。

## 三、⚠️ 两条硬约束（都是实测踩出来的）

1. **别把归属信息塞进"会被整体重写"的状态文件。**
   我们踩的实例：回复检查器每次运行都用 `JSON.stringify({updatedAt, seen})` **整体重写**它的水位线文件 ——
   往里加任何字段，**下一次运行就被抹掉**。
   ⇒ **判断法**：那个文件是"每次运行重写"还是"增量维护"？**前者不能加字段。**
2. **别用信箱当归档。**
   信是写给**会话实例**的（文件名就是那个 id）⇒ **会话一关，没读的信就成了孤儿**，
   后来的新会话（文件名不同）**不会**收到它。
   ⇒ 跨会话**必须留传**的事，要落在**按"事"组织**的地方（本表就是其中之一）。

## 四、消费端：只加不删的接法

给"回复检查器"加一层**只读**提示 —— **没有归属记录时，行为与从前完全一致**：

```js
// ① 常量区：只读辅助函数（含记忆化，避免同一 URL 反复读盘）
const OWNERS_PATH = path.join(os.homedir(), '.dsh', 'inflight', 'issue-owners.json');
const ownersCache = new Map();
function ownerFor(url) {
  if (ownersCache.has(url)) return ownersCache.get(url);
  let hit = null;
  const m = /^https:\/\/github\.com\/([^/]+)\/([^/]+)\/(?:issues|pull|discussions)\/(\d+)/.exec(url || '');
  if (m) {
    const key = (m[1] + '/' + m[2]).toLowerCase() + '#' + m[3];   // ⚠️ 大小写归一
    try {
      const table = JSON.parse(fs.readFileSync(OWNERS_PATH, 'utf8'));
      const idx = new Map();
      for (const [k, v] of Object.entries(table.owners || {})) idx.set(k.toLowerCase(), v);
      hit = idx.get(key) || null;
    } catch { hit = null; }   // 文件缺失/损坏 ⇒ 静默 null，行为与从前一致
  }
  ownersCache.set(url, hit);
  return hit;
}

// ② 文本输出段（在"链接:"那行之后加两行）
const owner = ownerFor(it.url);
if (owner) {
  const who = owner.session || '（归属表里没写 session）';
  const tag = owner.state && owner.state !== 'open' ? `（标记：${owner.state}）` : '';
  lines.push(`   👤 原提交者: ${who}${owner.sessionTitle ? ` · ${owner.sessionTitle}` : ''} —— 建议叫醒它处理，别自己回${tag}`);
}
```

**实际效果**：

```
1) [Issue 回复] owner/repo#123 （提交物标题）
   谁: someone   何时: 2026-01-01 18:29
   链接: https://github.com/owner/repo/issues/123#issuecomment-0000000
   👤 原提交者: <your-session-id> · （会话标题） —— 建议叫醒它处理，别自己回
```

## 五、⚠️ 三个实现坑（都实测踩过）

1. **大小写必须归一** —— GitHub 的 owner/repo **不区分大小写**，而这张表是**人手维护**的 ⇒
   精确匹配会**静默漏报**（最坏的一种失败：排查时看不见，还以为是"没人认领"）。
2. **会话标题常常自带括号** ⇒ **别再用括号包它**（会变成双括号），改用 ` · ` 分隔。
3. **"已回过的条目"不能当验证样本** —— 它会被"我回过没有"那条判据**过滤掉**，
   于是你**挑的样本早就过期了**，还以为是功能没生效。（我们就是这样自己给自己挖了个坑。）

## 六、验证姿势（安全，实测有效）

1. 往归属表**临时插入**一条、对应**"当前确实在列表里"**的条目（**借真实存在的键最稳**）；
2. 在**脚本的临时副本**上跑（复制到临时目录即可 —— 状态文件通常锚在脚本目录，**不污染真数据**）；
3. 看**正例**是否打印、**反例**是否**不**打印（**反例同样重要**）；
4. **恢复归属表，并在同一条命令里再读一次关键事实**（例如把记录数打出来）。

> ⚠️ **「我做了备份」不等于「还原成功」—— 还原之后必须再验一次。**
> （我们为另一件事写下的判据，在这张表上同样适用：那次"2 项 ≠ 1 项"的虚惊，正是靠"再验一次"才查清是预期错了、表其实是干净的。）

## 七、防膨胀

归属表**只增不减**会变成负担 —— 这是我们在别处已经治过一次的病（一张协调用的表涨到 **55 KB** 才做冷归档）。
⇒ 表自带 `cleanup` 约定：

1. **已闭环**（无人再回 / 原提交者已回复且对方未追问）⇒ **删掉**；
2. **原提交者会话已归档** ⇒ 保留但 `state` 标 **`degraded`**（对应"任何会话可接手"的降级分支）；
3. **硬上限 40 项**，超出时先清 `closed` 且 `degraded` 的。

## 八、与人的接口：**多线索指认**

回复到达时，**除了转交，还要提示人** —— 而且必须**多线索**：

```
❌ "#abc123 提的 issue 有回复了"
✅ "「（会话标题）」那只（今天 20:15 提的 owner/repo #123）有回复了"
```

**理由：人记不住会话 id。**（我们的实测：同一个人两次说"我印象里有只鲸鱼娘……"，两次都记不清是哪个 id。）
线索要**同时给**：**会话标题 + 时间 + 项目名**。

---

## 九、这一套和另外两份的关系

| 机制 | 回答的问题 | 载体 |
|---|---|---|
| **信箱** | "**我给某个会话留的话，它读了吗**" | 一个会话一个文件 |
| **台账** | "**现在谁在做什么、什么已经查过了**" | 一张所有人可见的表 |
| **归属与转交**（本文） | "**这条回复该谁去处理**" | 一张"事 → 会话"的表 |

三者**都是文件**，因为它们解决的是同一类问题：**在没有共享内存的多个 agent 之间，制造"可寻址"的协作。**
